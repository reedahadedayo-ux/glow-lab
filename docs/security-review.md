No customer rows, raw provider errors, decrypted Vercel secrets or private webhook names/destinations are included in the public files. The original upload and scan scratch artifacts remain outside tracked source. No history rewrite, customer deletion, database migration, trigger modification or email send was performed.

## Secret scanning: evidence and limits

`python3 scripts/audit-publication.py --all-refs` checks the tracked **working-tree versions** and blobs/messages reachable from all locally available refs; shallow history is rejected. It reports locations/rules, not matched values. It does not certify remote-only refs, GitHub attachments, hosted logs, screenshots OCR or the staged blob snapshot. Stage and inspect new files before relying on `git ls-files` scope; review the staged diff separately.

A separate offline `detect-secrets` scan was run over tracked files and full historical snapshots. Earlier reviewed flags were deliberate test-only session-secret canaries; the prepared source-tree scan flagged 16 locations, reviewed as test-only canaries, documentation of a secret variable, commit SHAs or Vercel deployment IDs. The full 26 pre-final ancestor snapshots produced 84 flags at nine test-canary locations; no confirmed credential. Final documentation changes are re-scanned before push. Online candidate validation is disabled. Neither a clean regex scan nor canary tests constitute a penetration test or proof that every kind of personal information was found.

The locally available original history was fetched before the earlier audit. No real customer emails/addresses were found in reviewed source fixtures; reserved example domains and obvious fictional data are used. Private author emails in commit metadata are separate from fixture data. The supplied raw blueprint key never entered Git, so no history rewrite was attempted for it.

## Credential response for the owner

1. Keep the original blueprint private and remove it from any public sharing surface if it has been shared there.
2. Identify the embedded credential privately; do not paste it in chat/issues. Assess its exposure and revoke/rotate through the authorised Supabase credential process.
3. Coordinate any consumers (server deployment, Make connections and other authorised services) to avoid breaking the working flow. Never silently rotate a live dependency during a documentation task.
4. Rebind Make using appropriate restricted/private connection storage. Avoid embedding broad credentials in future exports. Re-export and sanitise every time.
5. The temporary Groq preview scope was restored after testing; no key was decrypted/printed. Existing protected probe deployments retain their own snapshots—scope restoration does not revoke those. Review their lifecycle with the owner if stricter isolation is desired.
